# 결과 페이지 완료 안내 운영

## 구현 상태

고객 완료 안내는 MP3 첨부와 별개다. HTML의 **내 음악 듣기** 버튼과 텍스트 대안에 같은 고정 결과 페이지 주소를 넣는다. Gmail은 HTML 플레이어를 제공하는 화면으로 사용하지 않으며, 음악은 결과 페이지에서 재생한다. 최초 완료와 재신청 완료의 문구를 구분한다. 메일에 외부 이미지·추적 픽셀·스크립트를 넣지 않는다.

발송 기본값은 **비활성**이다. Gmail OAuth 연결이 있어도 그것만으로 고객 완료 안내를 시작하지 않는다. 이번 개발 중 실제 메일 추가 발송·새 음악 생성·기존 곡의 재신청·다운로드 소진은 실행하지 않았다.

## 설정과 등록

| 설정 | 용도 |
| --- | --- |
| `RESULT_PUBLIC_ORIGIN` | 운영자가 확정한 공개 HTTPS 원점. 예: `https://music.example.com`. 경로·query·fragment·별도 포트·로컬 IP 불허 |
| `RESULT_LINK_ENCRYPTION_KEY` | 독립적인 32바이트 난수의 base64url 인코딩(43자). 서버 Secret에만 보관 |
| `RESULT_EMAIL_ENABLED` | 정확히 `true`일 때만 신규 대기 건 발송 활성 |
| 기존 Gmail OAuth 3종·발신 주소 | 사용자에게 동의받은 발신 계정 |
| 기존 Supabase URL·서비스 역할 키 | 서버 전용 DB·Storage 접근 |

암호화 키를 채팅·명령 인자·Git·로그에 넣지 않는다. Secret 관리 시스템에서 생성·보관하며 관리자 토큰·DB 키·Gmail 키를 재사용하지 않는다. AES-256-GCM 암호문은 곡 ID·수신처·공개 원점을 추가 인증 데이터로 묶는다. 다른 곡·수신처·원점·키로 복호화하지 못한다.

서버 전용 `song_email_settings`에 수신처와 발신 주소·공개 원점·암호화된 페이지 토큰을 저장한다. 원본 토큰과 완성된 고객 URL은 DB 감사 기록에 저장하지 않는다. 기존 `song_result_links.token_hash`는 변경하지 않는다. RLS와 테이블/RPC 권한으로 anon·authenticated의 접근을 차단한다.

기존 링크의 비공개 파일이 있는 서버에서 다음 명령으로 등록한다. 이 명령은 발송하지 않는다.

```sh
npm run notification:configure -- --song-id <UUID> --recipient <EMAIL> --allow-save
```

`artifacts/result-links/<UUID>.json`의 발급 완료 상태와 곡 ID·토큰을 검증한다. 파일은 0600이어야 한다. DB의 기존 토큰 해시와 일치해야 등록된다. 파일이 없는 환경에서는 해시로 토큰을 복구하거나 기존 페이지를 재발급하지 않는다. 원래 환경의 비공개 보관 자료가 필요하다. 고객 수신처는 운영자가 확정한 주소만 등록한다.

암호화 키 교체는 자동 처리하지 않는다. 신규 키를 적용하기 전에 기존 링크 보관 자료로 재암호화하는 절차를 검토한다. 잘못된 키는 해당 발송 시도를 실패 처리하며 자동 재발송하지 않는다. 암호화 키를 잃어도 고객이 이미 가진 고정 페이지 링크 자체를 바꾸지 않는다.

## 대기 처리와 중복 방지

최초 설정 등록 시 현재 음악이 유효하면 `initial_ready`, 재신청 성공 시 기존 처리에서 `reissue_ready` 대기 행을 만든다. 곡·다운로드 차수마다 안내 행 하나만 허용한다. 설정을 다시 저장하거나 명령을 반복해도 이미 처리한 차수를 다시 보내지 않는다.

명시적 실행:

```sh
npm run notification:deliver -- --deliver-pending
```

실제 실행에는 발송 활성 설정도 필요하다. 옵션 없는 실행은 도움말만 표시한다. `result:serve` 및 `result:public`은 활성 설정이 있을 때 60초마다 신규 대기 건을 처리한다. 겹친 실행은 막고, 프로세스 종료 후에도 DB의 점유 상태로 중복을 막는다. 초기 요청 접수·결제 시스템은 아직 없어 임의의 고객 수신처를 자동 수집하지 않는다.

| 상태 | 의미 |
| --- | --- |
| `pending_setup` / `pending` | 신규 대기. 설정이 없는 건은 보내지 않음 |
| `sending` | 발송 시작을 DB에 기록. 프로세스 중단·응답 손실 시 확인 필요 |
| `sent` | Gmail 메시지 ID와 DB 확정 기록이 있음. 실제 받은편지함 수신 보장은 아님 |
| `failed` | 발송 전 검증·인증 실패 또는 명시적 거절. 자동 재시도 안 함 |
| `unknown` | 발송 중 응답 손실·서버 오류 등 결과 불명. 자동 재시도 안 함 |
| `skipped` | 만료·소진·차수 변경·페이지 취소 등으로 미발송 |

차수·음원 상태·페이지 유효성·수신처·원점·발신 주소를 DB에서 재확인하고 점유한다. 발송 전 복호화와 토큰 해시를 비교한다. 인증은 Google 계정 이메일까지 확인하고 실제 발송 POST는 한 번만 수행한다. 만료 시각도 발송 직전 확인한다. 이전 차수의 발송 확정이 새 차수의 안내 상태를 덮어쓰지 않는다.

`failed`·`sending`·`unknown`의 상태를 삭제하거나 `pending`으로 바꾸어 자동 재발송하지 않는다. 운영자가 DB operation_id와 Gmail 보낸편지함을 확인한 뒤 별도 결정을 해야 한다. 현재 서비스의 OAuth 권한에는 메일 읽기 권한이 없어 보낸편지함을 서버에서 자동 조회하지 않는다.

관리자 `/api/admin/notifications`와 **고객 완료 안내 이력**에서 상태를 읽을 수 있다. API에는 수신처·페이지 토큰·암호문·완성된 고객 URL을 포함하지 않는다. 관리자 화면은 내부 로컬 서버에만 있다.

## 미리보기와 검증

```sh
npm run notification:preview
npm test
```

미리보기는 예약된 예시 도메인·합성 토큰을 사용하며 실제 네트워크·DB·Gmail에 접근하지 않는다. HTML·텍스트 2종은 Git 제외 `artifacts/result-email-preview/`에 생성한다.

실제 Supabase에 `20261027154624 / result_email_notifications`를 적용했다. 롤백 트랜잭션으로 점유·중복 차단·다른 operation_id 거부·결과 불명 후 재시도 제외를 확인했다. 실제 Gmail로 연결되는 설정은 등록하지 않았다. 검증용 음악·대기 행은 남기지 않는다. 기존 원본 음악·다운로드 권한·MP3 직접 발송 감사 기록은 유지한다.

## 이후 설정할 항목

공개 서비스 주소와 호스팅 대상을 확정하고 `doc/RESULT_DEPLOYMENT.md`의 준비 절차를 적용한다. 별도 Secret과 기존 링크 자료를 연결한 뒤, 지정 수신처에 대한 결과 페이지 안내 테스트를 계획한다. 공개 배포·발송 활성화·실제 추가 메일은 이번 개발에서 실행하지 않았다.
