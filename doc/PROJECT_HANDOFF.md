## 1. 프로젝트를 만드는 이유와 제품의 마음

프로젝트 이름은 **노사연(Nosayeon)**이다. 이름에는 다음 두 가지 의미가 겹친다.

- 잘 알려진 사람 이름처럼 들려 제목 자체가 기억에 남고 바이럴 요소가 있다.
- 실제 서비스의 핵심인 **노래와 사연을 연결한다**는 의미가 들어 있다.

이 서비스는 사용자가 자신의 사연을 보내면, 그 사연을 바탕으로 AI가 하나의 노래를 만들어 주는 플랫폼이다.

중요한 것은 단순히 웃긴 이름을 앞세운 일회성 AI 음악 장난감이 되는 것이 아니다. 이름은 사람의 시선을 끌 수 있지만, 사용자가 맡긴 사연에는 진심과 감정이 들어 있으므로 결과물도 **사연을 존중하고 진심을 담은 음악**이어야 한다.

제품이 지향하는 경험은 대략 다음과 같다.

1. 사용자가 자신의 사연과 원하는 음악적 분위기를 전달한다.
2. 시스템이 이를 음악 생성 모델에 적합한 지시문으로 변환한다.
3. AI가 사연을 담은 노래를 생성한다.
4. 사용자는 이메일로 결과 페이지를 받는다.
5. 페이지에서 음악을 듣고, 정해진 정책에 따라 한 번 다운로드한다.
6. 파일이 만료된 뒤에도 일정 기간 안에는 동일한 음악을 다시 준비해 달라고 신청할 수 있다.

프로젝트 소유자가 중요하게 생각하는 우선순위는 다음과 같다.

- 초보자도 운영하고 이해할 수 있어야 한다.
- 가능한 한 무료 또는 저비용 서비스로 시작해야 한다.
- 처음부터 지나치게 복잡한 구조를 만들지 않는다.
- 생성 비용이 발생하는 음악을 실수로 중복 생성하지 않는다.
- 실패한 단계만 다시 실행할 수 있어야 한다.
- 테스트 단계에서는 문제를 눈으로 확인할 수 있도록 로그가 잘 보여야 한다.
- 처음 선택한 인프라에서 다른 서비스로 옮기는 부담을 줄이고 싶다.
- 모바일에서도 프로젝트를 계속 관리하고 개발 지시를 내릴 수 있어야 한다.

## 2. 협업 방식과 개발 원칙

### 2.1 역할

- 프로젝트 소유자: 제품 방향, 정책 및 최종 승인
- UI 담당 친구: 나중에 최종 화면의 HTML/UI 껍데기를 제작
- Codex: 기능 구현, API 연동, 백엔드 및 데이터 구조, 테스트, UI 껍데기와 기능 통합

### 2.2 UI 개발을 고려한 원칙

현재는 기능 검증용 테스트 페이지를 먼저 만든다. 나중에 UI 담당자가 HTML을 가져오면 기능을 쉽게 이식할 수 있도록 다음을 지킨다.

- 화면 마크업과 기능 로직을 분리한다.
- API 호출, 프롬프트 조합, 상태 관리, 로그 처리를 독립 모듈로 둔다.
- 특정 HTML 구조에 기능이 강하게 묶이지 않게 한다.
- UI 담당자가 사용할 수 있도록 필요한 DOM 요소, 이벤트, 상태값의 간단한 통합 계약을 남긴다.
- 실제 서비스에서는 최종 AI 프롬프트를 일반 사용자에게 노출하지 않을 예정이다.

### 2.3 안전 및 비용 원칙

- 음악 생성은 비용이 발생하므로 **자동 재생성하지 않는다**.
- 음악 생성 실패 시 사용자가 직접 재시도한다.
- 음악은 이미 생성됐는데 저장이나 이메일만 실패했다면 음악을 다시 만들지 않는다.
- API 키, OAuth 토큰, 보안 토큰은 브라우저 로그나 화면 로그에 출력하지 않는다.
- 비밀값은 Git에 커밋하지 않는다.
- 프로젝트 소유자는 비밀값을 채팅에 붙여 넣지 않는다.

## 3. 확정된 기술 구성

### 3.1 전체 구조

| 영역 | 선택한 서비스 | 역할 |
|---|---|---|
| 소스 저장소 | GitHub 비공개 저장소 | 코드와 문서 관리, 협업 |
| 개발 실행 환경 | Codex Cloud | PC가 꺼져 있어도 개발 작업, 모바일/웹/데스크톱에서 작업 이어가기 |
| 프런트엔드 호스팅 | Cloudflare Pages | 테스트 페이지와 결과 페이지 공개 |
| 데이터베이스 | Supabase Postgres | 음악 요청, 상태, 만료일, Interaction ID, 로그 등 저장 |
| 파일 저장소 | Supabase Storage 비공개 버킷 | MP3 임시 저장 |
| 서버 로직 | Supabase Edge Functions 중심 | 저장, 이메일, 보안 토큰 확인, 서명 URL, 재신청 처리 |
| 음악 생성 | Google Lyria 3.5 / Gemini API | 사연 기반 음악 생성 |
| 메일 | Gmail API 예정 | 생성 완료 및 재신청 완료 이메일 발송 |
| 카카오톡 | 추후 | 현재 범위 밖 |

### 3.2 왜 이렇게 선택했는가

- Supabase는 DB뿐 아니라 Storage와 Edge Functions까지 한곳에서 관리할 수 있고 초보자가 비교적 접근하기 쉽다.
- Supabase 무료 플랜의 파일 저장공간은 현재 확인 기준 1GB이므로 영구 보관이 아닌 임시 보관 정책을 사용한다.
- Supabase 자체는 무료 프런트엔드 호스팅 용도로 적합하지 않아 페이지는 Cloudflare Pages에 둔다.
- Cloudflare Pages는 GitHub 비공개 저장소와 연결할 수 있고 정적 페이지 배포에 적합하다.
- GitHub 저장소는 공개할 필요가 없으며 비공개로 운영한다.
- Codex Cloud 환경은 비공개 GitHub 저장소를 기반으로 생성·게시한 뒤 사용한다.

### 3.3 프로젝트 이동 계획

이 대화는 로컬 프로젝트에서 진행되었기 때문에 모바일에서 바로 보이지 않았다. 개발은 새 Cloud 작업에서 시작한다.

5. 비공개 GitHub 저장소를 연결하고 환경을 검사한 뒤 게시한다.
6. 게시된 환경으로 새 Codex Cloud 채팅을 시작한다.

## 4. 음악 생성 API에 대해 파악한 내용

### 4.1 용어 정리

초기 대화에서는 편의상 “Google Flow에서 음악을 생성하고 다시 다운로드한다”고 표현했다. 실제 자동화 구현에서 사용하는 것은 소비자용 Flow 화면이 아니라 **Google의 Lyria 모델을 Gemini API의 Interactions API를 통해 호출하는 방식**이다.

개발 문서와 코드에서는 혼동을 막기 위해 다음처럼 부른다.

- 모델: Lyria 3.5
- API: Gemini Interactions API
- 생성 결과의 고유 식별자: `interaction_id`
- Google에 보관된 기존 결과를 다시 가져오는 행위: 기존 Interaction 조회/복구
- 기존 결과가 없을 때 새로 모델을 호출하는 행위: 음악 재생성

두 행위를 절대 같은 것으로 취급하면 안 된다. 기존 음악을 복구해야 할 때 새 음악을 생성하면 비용과 결과물이 달라질 수 있다.

### 4.2 입력 방식

음악의 장르, 감정, 보컬, BPM, 구성, 가사, 길이 같은 대부분의 음악적 요구사항은 고정된 enum만 전달하는 방식이 아니라 **서술형 프롬프트에 명확하게 작성하는 방식**이 중심이다.

따라서 실제 서비스에는 다음 과정이 필요하다.

```text
사용자가 입력한 사연과 선택 옵션
→ 내부 프롬프트 빌더
→ Lyria에 전달할 서술형 지시문
→ 음악 생성
```

테스트 화면에서는 프롬프트를 빠르게 바꿔 보기 위해 옵션과 직접 편집 기능을 모두 제공한다. 실제 서비스에서는 최종 프롬프트를 사용자에게 숨길 예정이다.

### 4.3 모델/API 관련 확인 사항

- `lyria-3.5`: 전체 노래 생성용 모델로 파악됨
- `lyria-3-clip-preview`: 짧은 클립용으로 파악됨
- 생성 결과에는 음악 파일뿐 아니라 가사/구성 텍스트가 포함될 수 있다.
- 음악 파일은 MP3 또는 WAV 형태로 받을 수 있으나, 저장공간 절약을 위해 이 프로젝트는 MP3를 우선한다.
- 정확한 곡 길이는 프롬프트 요청과 완전히 일치하지 않을 수 있다.
- API 생성 결과에는 SynthID 워터마크 및 안전 필터가 적용될 수 있다.
- 현재 파악한 API 흐름은 한 번에 전체 곡을 생성하는 방식이며, 생성된 곡을 대화식으로 세밀하게 편집하는 기능은 별도 검증이 필요하다.

### 4.4 비용에 관한 당시 확인 내용

가격은 변경될 수 있으므로 개발 직전 공식 가격표를 다시 확인해야 한다.

- 당시 파악한 Lyria 3.5 API 가격: 요청 1회당 약 USD 0.08
- 당시 단순 환율 가정 USD 1 = KRW 1,400 적용 시 약 112원/곡
- Flow 소비자용 구독 가격과 Gemini API 사용료는 별개다.
- 자동화 서비스이므로 구독형 Flow 화면이 아니라 API 비용을 기준으로 사업성을 계산해야 한다.

### 4.5 Interaction 저장과 복구

공식 문서 기준으로 Interactions API는 기본적으로 `store=true`일 때 Interaction을 저장하고 고유 ID를 반환한다.

- 유료 프로젝트 기본 보관기간: 최대 55일
- 무료 프로젝트 보관기간: 1일
- 유료 프로젝트 설정 가능 기간: 7일, 14일, 28일, 55일
- 만료되거나 삭제된 Interaction은 다시 가져올 수 없다.
- 동일한 Google 프로젝트의 정상 인증정보가 필요하다.

이 프로젝트는 음악 생성 API가 유료 사용이므로 Google AI Studio에서 보관기간을 **55일**로 설정할 계획이다. 사용자에게는 경계 시점의 위험을 피하기 위해 재신청 가능 기간을 **생성일로부터 최대 50일**로 제한한다.

다만 다음은 아직 실제 Lyria 응답으로 검증되지 않은 핵심 가정이다.

> `interaction_id`로 Interaction을 다시 조회했을 때 최초 생성 시 받은 MP3와 완전히 동일한 오디오 데이터를 다시 획득할 수 있는가?

공식 스키마상 AudioContent에는 데이터 또는 URI가 포함될 수 있고 전체 Interaction을 `get`으로 조회할 수 있다. 그러나 이 제품의 보관 정책을 여기에 의존하기 전에 실제 Lyria 호출로 파일 해시까지 비교해야 한다.

## 5. 확정된 파일 보관·스트리밍·다운로드 정책

이 정책은 여러 차례 논의 후 단순하게 확정한 내용이다. 임의로 복잡하게 바꾸지 않는다.

### 5.1 사용자에게 보여줄 핵심 정책

> 다운로드 링크는 1회만 사용할 수 있으며, 사용하지 않더라도 발급일로부터 최대 7일간 유효합니다. 음악 생성일로부터 50일 이내에는 새로운 링크를 다시 신청할 수 있습니다.

### 5.2 최초 생성

1. 음악 생성이 완료되면 MP3를 Supabase Storage의 비공개 버킷에 저장한다.
2. 음악 및 요청 메타데이터와 Google `interaction_id`를 DB에 저장한다.
3. 결과 페이지 링크를 이메일로 **최초 1회 자동 발송**한다.
4. 링크 발급일로부터 최대 7일 동안 페이지에서 스트리밍과 다운로드가 가능하다.
5. 다운로드 링크는 1회성이다.

### 5.3 다운로드 버튼 클릭

“다운로드 완료”를 브라우저에서 정확하게 감지하기 어렵기 때문에 다음처럼 정의한다.

- 사용자가 **다운로드 버튼을 누른 순간** 1회 사용한 것으로 처리한다.
- 음악 재생만으로 다운로드 횟수를 소진하지 않는다.
- 파일 전송 자체를 시작하지 못한 서버 오류라면 가능하면 횟수를 소진하지 않게 처리한다.
- 정상적인 다운로드 요청이 시작되면 다운로드 권한을 만료 처리한다.
- Supabase에 저장된 MP3를 삭제한다.
- 결과 페이지의 플레이어와 다운로드 버튼을 제거한다.
- 페이지 해당 영역에 `다운로드 링크가 만료되었습니다` 또는 이에 준하는 상태를 표시한다.

다운로드 도중 사용자 인터넷이 끊기거나 사용자가 취소한 경우에도 버튼을 누른 시점에 사용 완료로 처리될 수 있다. 이 경우 사용자는 새 링크를 다시 신청한다. 이 단순한 정책을 사용자가 이해할 수 있게 안내한다.

### 5.4 7일 동안 다운로드하지 않은 경우

- 링크가 자동 만료된다.
- Supabase의 MP3를 삭제한다.
- 플레이어와 다운로드 버튼을 제거한다.
- 결과 페이지에 만료 상태와 재신청 버튼을 표시한다.

### 5.5 다시 신청

1. 생성일로부터 50일 이내라면 결과 페이지에 `다운로드 링크 다시 신청` 버튼을 보여준다.
2. 사용자가 신청하면 Google의 기존 `interaction_id`로 **같은 음악**을 다시 가져온다.
3. MP3를 Supabase에 다시 저장한다.
4. 신청 후 최대 10분 이내에 새로운 결과 링크를 이메일로 발송한다.
5. 새 링크도 1회성이며, 사용하지 않으면 발급일로부터 최대 7일 동안 유효하다.
6. 새 링크로 다운로드하면 동일하게 Supabase 파일을 삭제하고 플레이어를 만료 처리한다.

`10분 이내`는 사용자에게 약속하는 처리 시간의 상한이다. 시스템이 고의로 10분을 기다리는 것이 아니다. 준비가 끝나면 즉시 발송한다.

### 5.6 50일이 지난 경우

- 새 다운로드 링크를 신청할 수 없다.
- 재신청 버튼을 비활성화하거나 숨긴다.
- `음악 보관기간이 종료되었습니다`라고 표시한다.

### 5.7 아직 결정이 필요한 경계 정책

다음 한 가지는 최종 결정되지 않았다.

- 생성 후 50일째에 재신청하면 새 링크를 발급일로부터 7일간 유효하게 둘 것인가?
  - 이렇게 하면 최종 다운로드 가능 시점은 생성 후 최대 57일이 될 수 있다.
  - 또는 링크 만료일을 `발급일 + 7일`과 `생성일 + 50일` 중 더 이른 날로 제한할 수 있다.

개발 전에 제품 소유자의 승인이 필요하다.

## 6. 결과 페이지 구조

음악마다 새로운 HTML 파일을 만드는 구조가 아니다. **결과 페이지 HTML은 하나**이고, URL의 음악 ID와 보안 토큰에 따라 데이터만 다르게 표시한다.

개념 예시:

```text
https://서비스도메인/result.html?id=SONG_ID&token=RANDOM_SECRET
```

페이지 동작:

1. URL에서 음악 ID와 토큰을 읽는다.
2. 서버가 토큰을 검증한다.
3. 현재 상태와 만료일을 조회한다.
4. 사용 가능하면 플레이어와 다운로드 버튼을 보여준다.
5. 7일 만료 또는 다운로드 사용 완료면 플레이어를 제거하고 만료 상태를 보여준다.
6. 생성일로부터 50일 이내라면 재신청 버튼을 보여준다.
7. 50일이 지났다면 보관 종료 상태를 보여준다.

### 보안 원칙

- Supabase Storage 버킷은 비공개로 한다.
- 서비스 역할 키는 프런트엔드에 절대 넣지 않는다.
- 결과 페이지용 원본 토큰은 DB에 그대로 저장하기보다 해시 저장을 우선 검토한다.
- Storage signed URL은 서버에서 짧게 발급한다.
- 결과 페이지 주소와 Storage 실제 파일 URL은 구분한다.
- 이메일에는 너무 짧은 Storage signed URL을 직접 넣지 않고 서비스의 안정적인 결과 페이지 URL을 넣는다.

### 구현 시 주의

브라우저 오디오 플레이어는 한 파일을 여러 Range 요청으로 나누어 가져올 수 있다. 따라서 Storage URL 자체를 “첫 HTTP 요청 시 무조건 소진되는 1회성 URL”로 만들면 스트리밍이 깨질 수 있다.

제품 정책상의 1회 사용은 **다운로드 버튼 이벤트**를 기준으로 관리하고, 스트리밍 요청과 분리해야 한다.

## 9. 오류 처리와 로그

비용이 드는 음악 생성을 자동으로 반복하지 않는다. 단계별 상태를 독립적으로 관리한다.

| 실패 단계 | 처리 원칙 |
|---|---|
| 음악 생성 실패 | 오류 표시 후 사용자가 직접 재시도 |
| 음악 생성 성공, Supabase 저장 실패 | 생성된 결과를 확보할 수 있다면 저장 단계만 재시도 |
| 결과 링크 생성 실패 | 링크 생성 단계만 재시도 |
| 이메일 발송 실패 | 결과 링크를 화면에 보여주고 이메일만 재발송 |
| 재신청 복구 실패 | 새 음악을 자동 생성하지 않고 기존 Interaction 복구만 재시도 |
| 전체 성공 | 음악 생성 및 이메일 발송 완료 상태 표시 |

### 테스트 로그 요구사항

- 단계마다 로그 버튼을 둔다.
- 로그에 시간, 단계, 성공/실패, HTTP 상태, 안전하게 정리한 오류 메시지를 남긴다.
- API 키, Gmail 토큰, 서비스 키, 결과 페이지 원본 토큰, 전체 오디오 Base64는 로그에 남기지 않는다.
- 음악 생성 요청에는 중복 클릭 방지를 위한 처리 중 상태가 필요하다.
- 재시도 시 동일 생성 건인지 새 생성 건인지 구분한다.

## 10. 상태 모델 초안

```text
draft
generating
generation_failed
generated
storage_failed
stored
email_pending
email_failed
available
download_consumed
expired_7d
restore_requested
restoring
restore_failed
restored
retention_ended
```

하나의 거대한 상태 문자열만 쓰기보다 다음처럼 단계별 상태를 분리하는 편이 재시도에 유리할 수 있다.

- `generation_status`
- `storage_status`
- `delivery_status`
- `download_status`
- `restore_status`

최종 스키마는 구현 전에 단순성과 재시도 요구를 비교하여 확정한다.

### `songs` 또는 유사 테이블의 후보 필드

| 필드 | 목적 |
|---|---|
| `id` | 내부 음악 ID |
| `google_interaction_id` | Google에서 동일 음악을 복구하기 위한 ID |
| `prompt` | 실제 생성에 사용한 프롬프트, 개인정보 정책 검토 필요 |
| `options` | 장르/보컬/분위기 등 당시 옵션 |
| `storage_path` | 현재 Supabase MP3 위치 |
| `status` 또는 단계별 상태 | 처리 상태 |
| `recipient_email` | 결과를 받을 이메일 |
| `access_token_hash` | 결과 페이지 접근용 토큰 해시 |
| `created_at` | 최초 생성 시각 |
| `issued_at` | 현재 링크 발급 시각 |
| `expires_at` | 현재 링크의 7일 만료 시각 |
| `downloaded_at` | 다운로드 버튼 사용 시각 |
| `restore_requested_at` | 재신청 시각 |
| `google_recovery_deadline` | 내부 복구 마감 시각 |
| `last_error_stage` | 최근 실패 단계 |
| `last_error_message` | 정제된 오류 내용 |

로그를 별도 테이블로 둘 경우 `song_id`, 단계, 이벤트, 안전한 상세정보, 생성시각을 저장한다.

## 11. API 키와 비밀정보 운영 방향

### 테스트 페이지

- 음악 API 키는 매번 사용자가 입력한다.
- 브라우저 저장소, DB, 소스코드에 저장하지 않는다.
- 직접 브라우저에서 Lyria API를 호출할 수 있는지는 CORS와 Google 정책을 실제로 검증해야 한다.

### 실제 서비스

실제 서비스에서 사용자가 API 키를 입력하게 하는 구조는 적합하지 않다. 운영 단계에서는 프로젝트 소유자의 Google API 인증정보를 서버 비밀값으로 관리하는 방향이 유력하다.

이렇게 해야 다음이 가능하다.

- 사용자가 키를 다시 입력하지 않아도 음악 생성
- 동일 Google 프로젝트의 `interaction_id`로 자동 복구
- 브라우저에 키를 노출하지 않음
- 비용과 할당량을 서버에서 통제

다만 Supabase 무료 Edge Function은 현재 확인 기준 요청 유휴 시간과 실행 시간 제한이 있으므로, 전체 곡 생성 시간이 제한을 넘는지 먼저 검증해야 한다.

## 12. Supabase 저장공간 운영

당시 확인한 Supabase 무료 플랜의 파일 저장공간은 1GB였다. 가격과 할당량은 변경될 수 있으므로 프로젝트 생성 시 다시 확인한다.

MP3 크기 예시:

- 2~3분, 128~320kbps일 때 대략 1.9~7.2MB 가능
- 평균 5MB로 단순 가정하면 1GB에 약 200곡이지만 여유공간과 기타 파일을 고려하면 더 적게 잡아야 한다.

현재 확정된 7일 임시 보관 및 다운로드 후 삭제 정책을 적용하면 무료 공간을 훨씬 효율적으로 쓸 수 있다.

자동 정리 작업은 다음을 처리해야 한다.

- `expires_at`이 지난 Supabase 파일 삭제
- DB 상태를 `expired_7d` 등으로 변경
- 고아 파일과 DB 레코드 불일치 점검
- Storage 삭제는 SQL에서 레코드만 지우지 말고 Supabase Storage API를 사용

## 14. 개발 전에 반드시 검증할 기술 사항

다음은 문서만 믿고 제품 구조를 확정하면 안 되는 항목이다.

### 최우선 검증: 동일 음악 복구

1. Lyria 3.5로 테스트 음악 1곡 생성
2. 응답의 `interaction_id` 저장
3. 최초 MP3 파일과 해시 저장
4. `interactions.get(interaction_id)` 호출
5. 오디오 데이터 또는 URI 추출
6. 다시 받은 파일의 해시를 최초 파일과 비교
7. 동일하면 복구 정책 사용
8. 다르거나 오디오를 다시 받을 수 없으면 보관 정책을 재설계

이 검증이 실패하면 “Supabase에서는 7일 후 삭제하지만 50일까지 같은 음악 재다운로드 가능”이라는 핵심 정책을 구현할 수 없다.

### 실행 시간 검증

- 전체 곡 생성이 Supabase Edge Function 무료 플랜 제한 안에서 완료되는가?
- 비동기 Interaction/background 실행 후 폴링 구조를 사용할 수 있는가?
- 브라우저 직접 호출이 CORS 및 키 보안 측면에서 테스트 전용으로 가능한가?

### 1회 다운로드 검증

- 다운로드 버튼 클릭 상태를 원자적으로 사용 완료 처리할 수 있는가?
- 중복 클릭과 여러 브라우저 탭의 동시 요청을 막을 수 있는가?
- 서버 오류로 전송을 시작하지 못한 경우 사용권을 되돌릴 수 있는가?
- 삭제 직후 진행 중인 다운로드와 오디오 Range 요청이 어떻게 동작하는가?

### 이메일 검증

- Gmail OAuth 설정과 refresh token 갱신
- 동일 주소에서 동일 주소로 정상 발송
- 스팸 분류 여부
- 재신청 후 10분 이내 발송 보장

## 19. 새 Codex 작업자에게

이 프로젝트에서는 기능을 많이 넣는 것보다 사용자가 맡긴 사연을 존중하고, 비용이 발생하는 음악 생성과 파일 수명을 명확하게 통제하는 것이 더 중요하다.

다음 원칙을 유지한다.

1. 이미 만들어진 음악을 복구해야 할 때 새 음악을 생성하지 않는다.
2. 음악 생성, 저장, 링크, 이메일 단계를 분리해 실패한 단계만 다시 처리한다.
3. 확정된 제품 정책을 기술 편의 때문에 조용히 바꾸지 않는다.
4. 미확정 사항은 임의 결정하지 말고 선택지와 영향을 설명한 뒤 승인을 받는다.
5. UI 담당자의 HTML을 나중에 쉽게 붙일 수 있게 기능을 분리한다.
6. 초보 운영자가 로그를 보고 현재 상태를 이해할 수 있게 한다.
7. 비밀정보와 사용자의 사연을 안전하게 다룬다.
8. 첫 구현은 반드시 Lyria Interaction 동일 음원 복구 검증부터 시작한다.

이 문서를 읽은 뒤에는 먼저 다음을 보고한다.

- 프로젝트 목적을 어떻게 이해했는지
- 이미 확정된 사항
- 아직 승인이 필요한 사항
- 가장 먼저 검증할 기술 가정
- 제안하는 첫 작업 단위

프로젝트 소유자가 확인하기 전에는 광범위한 개발을 시작하지 않는다.
