# 노사연 관리자 페이지 구성안

작성: 2026-10-31, 한국 시간. **릴리즈 범위를 정하기 위한 추천안**이며 기능 전체가 구현됐다는 뜻은 아니다. 고객 신청/결과 UI와 분리해 운영자가 서비스 상태를 확인하고 문제를 처리하는 화면으로 구성한다.

## 현재 관리자 페이지가 있는가?

관리자 화면 코드는 `web/admin.html`, 동작 코드는 `web/js/admin.mjs`, API는 `src/admin-access.mjs`에 있다. `npm run result:serve`로 실행하는 로컬 서버의 `/admin.html`에서 사용하도록 만든 내부 운영 도구다. 이번 확인은 코드 기준이며 로컬 서버 실행 상태는 검증하지 않았다.

현재 공개 Site의 빌드에는 관리자 화면/API가 포함되지 않는다. 따라서 지금 고객 사이트 주소 뒤에 `/admin.html`을 붙여 사용할 수 있는 배포된 관리자 페이지는 없다.

| 코드에 있는 기능 | 현재 범위와 보완점 |
| --- | --- |
| 관리자 인증 | 별도 관리자 토큰/로컬 인증 파일 방식. 외부 운영 배포용 로그인·권한·세션 관리 필요. |
| 운영 통계 | 등록된 곡 중심의 생성·보관·복구 통계. 전체 신청 수와 생성 전 실패 수는 `song_requests` 연결 필요. |
| 음악 목록 | 곡 ID 검색·페이지 이동·원본 정보·다운로드 상태 조회. 신청 상세와 연결 필요. |
| DB/파일 용량 | 사용량 및 기준 용량을 설정한 경우 잔여량 조회. 실제 서비스 요금제와 청구액은 별개. |
| 백업 MP3 직접 전달 | 운영자가 가진 원본 파일을 해시로 검증해 준비/전달. 백업 파일을 자동 보유하는 기능은 아님. |
| 메일 이력 | 고객 완료 안내 및 직접 전달 이력 조회. 신청별 연결·필터·오류 확인 강화 필요. |

## 추천 메뉴와 1차 릴리즈 범위

| 메뉴 | 들어갈 주요 항목 | 우선순위 |
| --- | --- | --- |
| 운영 현황 | 신청 가능 여부, 작업자 상태, 대기/처리/완료/오류 수, 조치 필요 목록 | 필수 |
| 신청·대기열 | 신청 검색·필터, 접수 순서, 진행 단계, 예상 시간, 신청 상세 진입 | 필수 |
| 신청 상세 | 사연/옵션/수신처, 처리 타임라인, 음악·다운로드·재신청·메일 연결 | 필수 |
| 오류·복구 | 실패 단계/코드, 결과 불명, 오래 멈춘 작업, 기존 결과 조회 및 수동 처리 | 필수 |
| 이메일 | 완료 안내/직접 전달 이력, 발송 실패/결과 불명, 수신처 확인 | 필수 |
| 음악·저장소 | 음악 보관 상태, 원본 정보, 다운로드 차수·기한, 삭제 대기/실패 | 필수 조회 |
| 운영 설정 | 신규 접수 중지/재개, 신청 한도, 연동 상태, 현재 배포 정보 | 최소 필수 |
| 관리자·변경 이력 | 관리자 로그인/권한, 운영자가 한 조치·설정 변경 기록 | 외부 배포 전 필수 |

처음에는 조회·검색·문제 탐지·제한된 수동 처리부터 완성한다. 통계 그래프, 자유로운 큐 재정렬, 복잡한 계정 관리 화면은 후순위로 둔다.

## 1. 운영 현황 — 첫 화면

첫 화면에서 **지금 신청을 받고 음악을 정상 처리하고 있는지** 판단할 수 있어야 한다.

- 서비스 상태: 정상 / 신규 접수 중지 / 처리 지연 / 작업자 연결 끊김.
- 작업자: 마지막 정상 신호 시각, 마지막 작업 완료 시각, 현재 작업과 경과 시간.
- 오늘 신청·완료·실패 수, 현재 대기·처리 중 수, 메일 확인 필요 수.
- 최근 24시간 신청 수 / 한도 50회, 남은 신청 수.
- 가장 오래 대기 중인 시간, 최근 평균 처리 시간과 예상 시간 산정 가능 여부.
- 조치 필요 목록: 작업자 중단, 오래 멈춘 생성, 결과 불명, 메일 실패, 파일 삭제 실패.
- 마지막 데이터 갱신 시각과 새로고침/자동 갱신 상태.

‘오늘’은 한국 날짜 기준, ‘신청 한도’는 최근 24시간 기준으로 구분한다. 생성된 곡 수를 전체 접수 수로 표시하지 않는다. 조회에 실패하면 ‘확인 불가’로 표시하고 0건으로 대체하지 않는다.

## 2. 신청·대기열

표의 기본 열은 **접수 시각 / 신청 번호 / 이메일 / 상태 / 대기 순서 / 경과·예상 시간 / 오류 표시 / 상세보기**로 한다.

- 접수일, 상태, 이메일, 신청 번호·곡 ID로 검색/필터.
- 대기 중 신청과 현재 실행 중 작업을 구분하고 자동 갱신.
- 신규 음악과 기존 곡 재신청을 구분하되 전체 처리 순서를 확인.
- 현재 FIFO 순서와 한 번에 한 작업 실행 상태 표시.
- 오래 대기하거나 처리가 멈춘 건을 눈에 띄게 표시.
- 개인정보가 들어간 이메일은 목록에서 일부 마스킹, 상세에서 권한에 따라 확인.

**취소는 아직 실행 전인 대기 건에만 제공하는 것을 권장**한다. 취소 기능은 새 개발이며 작업 배정과 충돌하지 않도록 DB에서 처리해야 한다. 생성 중인 곡을 취소했다고 이미 발생한 비용이 사라지는 것처럼 표시하지 않는다. 임의 순서 변경은 1차 범위에서 제외한다.

## 3. 신청 상세

한 신청의 전체 경과를 한 화면에서 연결한다.

- 신청 번호·접수 시각·상태·수신 이메일·사연·음악 옵션.
- 접수 → 제작 시작 → 생성 결과 확인 → 검증 → 저장 → 링크 준비 → 메일 접수의 타임라인.
- 각 단계의 시작·완료·경과 시간, 실패 코드와 이해하기 쉬운 설명.
- 생성 요청 체크포인트 존재 여부, 연결된 곡 ID와 다운로드 차수.
- 음악 재생 가능 여부, 파일 크기·형식·원본 일치 여부, 저장/삭제 상태.
- 고객 다운로드 가능 여부·만료 시각·사용 완료 시각, 재신청 가능 기한·이력.
- 해당 신청의 메일 이력과 운영자 조치 이력.

관리자 미리 듣기는 고객의 1회 다운로드 권한을 소진하지 않는 경로로 제공한다. 곡의 고정 결과 페이지는 유지하며 원본 링크 토큰을 기본 목록/로그에 노출하지 않는다. Google 요청 식별자는 운영 확인용이고 비밀번호·키와는 구분해 접근을 제한한다.

## 4. 오류·복구 — 가장 먼저 보강할 운영 기능

다음 상황을 구분해서 보여준다.

| 상황 | 관리자가 확인할 내용 | 권장 처리 |
| --- | --- | --- |
| 생성 요청 결과 불명 | 요청을 보냈는지, 체크포인트가 있는지 | 자동 생성 금지. 기존 요청을 확인하고 운영 확인 필요 상태로 보존. |
| 음악은 생성됐으나 검증/저장 실패 | 기존 생성 결과, 실패 단계, 원본 데이터 검증 | 같은 결과를 조회해 실패 단계부터 수동으로 이어가기. |
| 오랫동안 처리 중 | 작업자 상태, 현재 단계·경과 시간 | 원인 확인 후 안전한 후속 조치. 신청을 단순히 accepted로 되돌리지 않기. |
| 메일 실패/결과 불명 | 발송 전후 상태, 중복 방지 기록, Gmail 접수 여부 | 미발송이 확인된 경우에만 명시적 수동 발송. 결과 불명은 먼저 대조. |
| 삭제 실패 | 삭제 대상과 현재 저장 상태 | 삭제 작업만 다시 수행. 음악 생성/메일을 다시 실행하지 않기. |

추천 버튼은 **상태 다시 확인 / 기존 생성 결과 확인 / 실패 단계 이어가기 / 운영 확인 완료·메모**다. 실제 동작은 해당 단계와 권한에 따라 제한한다. ‘다시 시도’ 하나로 생성·저장·메일을 전부 반복하지 않는다.

사용자가 건너뛰라고 한 실패 신청은 표시·메모만 유지하고 복구 대상에서 제외한다. 관리자 조치에는 대상·영향·실행자를 기록한다.

## 5. 이메일

- 최초 완료 안내 / 재신청 완료 안내 / 백업 MP3 직접 전달을 구분.
- 신청/곡/다운로드 차수, 받는 사람, 발신 계정, 요청·접수 시각 조회.
- 준비 중 / 발송 중 / Gmail 접수 완료 / 실패 / 결과 불명 표시.
- 발송 실패 코드, 중복 방지 기록, 해당 신청 상세로 이동.
- 수신처와 기존 발송 이력을 확인하는 수동 발송 화면.

Gmail 접수 완료를 받은편지함 도착이나 열람 완료로 표시하지 않는다. 현재 연동은 발송 중심이며 보낸편지함 자동 조회 기능이 있다고 가정하지 않는다. 수신처 변경·재발송은 기존 이력을 덮어쓰지 않고 별도 조치로 기록한다.

## 6. 음악·저장소

- 생성된 음악/파일 수, 저장 중·저장 완료·삭제 대기·삭제 실패·삭제 완료 수.
- 파일별 형식·바이트 수·해시·최초 생성 시각, 원본 검증 결과.
- 재신청 차수별 저장/다운로드/소비/삭제 이력.
- DB 용량, 음악 파일/프로젝트 저장 용량, 기준 용량 대비 사용량.
- 기한 경과 파일과 정리 작업 결과, 마지막 정상 정리 시각.
- 원본 백업이 실제로 있는지와 복구 출처를 구분.

관리자용 파일 전달은 기존 검증된 MP3 전달 기능을 재사용한다. Google Drive 백업은 아직 없으므로 ‘백업 완료’로 표시하지 않는다. 보관기간·삭제 정책은 현재 제품 정책을 유지한다.

## 7. 운영 설정·상태

- **신규 접수 중지/재개**: 이미 접수된 건의 처리와 구분해서 제어하도록 개발.
- 최근 24시간 신규 신청 한도(현재 50회), 한 번에 실행하는 작업 수(현재 1개).
- Google 생성, Gmail, DB·Storage 연결의 마지막 확인 결과/시각.
- 사이트/작업자 배포 버전과 환경 구분(테스트/운영).
- 알림 수신 대상·알림 종류: 작업자 중단, 장기 지연, 오류 증가, 메일·삭제 실패, 사용량 임계치.

현재 runtime.enabled는 접수와 작업자 처리에 함께 영향을 주므로 이를 그대로 ‘신규 접수만 중지’ 버튼에 연결하면 안 된다. 용도를 분리한 제어가 필요하다. 기존 큐 정리나 작업 중단 버튼도 각각 영향 범위를 명시해야 한다.

동시 처리 수를 설정 화면에서 바꾸기만 하면 병렬 생성이 되는 구조는 아니다. 병렬 처리 확대는 큐·잠금·API 한도·비용 검증이 필요한 별도 개발이다. 실제 비용은 청구 근거를 연결할 수 있을 때 표시하고, 추정 비용은 구분한다.

## 8. 관리자 접근·변경 이력

- 신청 페이지의 공용 입장 비밀번호와 관리자 인증을 분리.
- 릴리즈 초기에도 운영자 개인별 로그인, 세션 만료/로그아웃, API별 권한 확인.
- 최소한 조회 권한과 발송·복구·설정 변경 권한 구분.
- 변경 이력: 실행자, 시각, 대상, 작업, 이유, 변경 전후 값, 결과.
- 비밀번호·OAuth 토큰·DB 서비스 키·고객 링크 토큰은 표시/다운로드/로그 저장하지 않음.
- 개인정보·사연은 필요한 화면/권한에서만 조회. 운영 통계 다운로드는 필요한 열만 제공.

키 변경은 해당 서비스의 Secret 관리 기능을 사용한다. 관리자 화면에 모든 키를 보여주거나 입력받아 저장하는 기능을 기본으로 만들지 않는다.

## 추천 화면 배치와 개발 순서

첫 화면 상단은 **서비스 상태 → 오늘 지표/24시간 한도 → 조치 필요 → 현재 대기열** 순으로 배치한다. 메뉴는 운영 현황 / 신청·대기열 / 오류·복구 / 이메일 / 음악·저장소 / 설정·변경 이력으로 묶고, 신청 상세는 목록에서 연다.

1. 신청/대기열/작업자 상태를 관리자 API에 연결하고 오류 조회부터 완성.
2. 외부 관리자 로그인·권한·변경 이력을 갖춘 뒤 관리자 전용 주소에 배포.
3. 기존 생성 결과 이어가기, 확인된 미발송 건의 수동 발송 등 조치를 단계별 연결.
4. 접수 제어·사용량/알림·모바일 확인을 마친 뒤 릴리즈 점검.

## 범위 확정 때 남길 운영 결정

필수 기능을 확정한 뒤 아래 항목은 2~3개 선택지로 좁혀 결정한다. 현재 정책을 임의 변경하지 않는다.

- 관리자 수와 조회/조치 권한 분리 수준.
- 대기 신청 취소 시 최근 24시간 한도 집계 방식(현재는 접수 건을 기준으로 집계).
- 수신처 변경·확인된 미발송 재처리의 운영 절차.
- 운영 알림 채널 및 임계치. 실제 알림 연동은 채널과 수신 대상을 정한 뒤 구현한다.

상시 작업자 호스팅, 로그 보존/수동 복구, 알림과 접근 권한 등 릴리즈 작업은 `doc/WORK_LOG.md`와 함께 갱신한다. 이번 작업은 구성안 문서화이며 관리자 공개 배포·운영 기능 실행은 하지 않았다.
