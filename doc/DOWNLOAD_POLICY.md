# 1회 다운로드와 사용 후 파일 삭제

## 동작

결과 페이지의 `노래 다운로드 · 1회` 버튼이 `POST /api/download?id=<UUID>`를 호출한다. 기존 결과 토큰을 Authorization 헤더로 보내고 서버가 곡 ID·기간·취소·사용 완료 여부를 검증한다. 별도 생성 API나 Google 재조회는 호출하지 않는다.

1. DB의 조건부 UPDATE로 10분간 다운로드 점유권을 확보한다. 한 작업만 점유할 수 있고, 중복 요청은 HTTP 409를 반환한다. GET 요청으로 권한을 소진할 수 없다.
2. 최대 8개·합계 64MiB인 모든 원본을 읽어 경로·MIME·크기·SHA-256을 확인한다. 한 파일은 MP3/WAV 그대로, 여러 파일은 ZIP 하나로 전달한다. ZIP은 무압축이며 파일명은 서버가 `original-1.mp3` 같은 고정 형식으로 만든다.
3. 응답 바이트를 모두 준비하고 연결·만료 여부를 확인한 뒤 현재 점유권으로 `consumed_at`을 원자적으로 기록한다. 점유 만료·취소·기간 만료·다른 작업의 점유권이면 확정하지 않는다.
4. 확정 전 준비 오류는 현재 점유권만 해제한다. 해제 요청까지 실패하면 10분 만료 후 수동 재시도가 가능하다. 사용 확정 후에는 네트워크 응답을 잃어도 권한을 되돌리지 않는다. 음악 재생성이나 다운로드 POST 자동 재시도는 없다.
5. 서버가 HTTP 응답을 마치거나 연결이 닫히면 사용 완료 파일의 삭제를 시작한다. 삭제 대상은 사용 완료된 해당 곡의 검증된 오브젝트 경로뿐이다. Storage API를 사용하며 Storage 테이블을 SQL로 삭제하지 않는다.
6. POST 방식의 Storage 목록 API에서 정확한 파일명이 사라졌음을 확인하면 링크의 `cleanup_status`와 음악의 `storage_status`를 `deleted`로 바꾼다. 삭제 직후 음원 GET은 CDN에 남을 수 있어 삭제 완료 판정에 사용하지 않는다. 일부 삭제·삭제 확인·완료 기록이 실패하면 사용 완료 상태를 유지하고 삭제만 재개할 수 있다. 기존 `storage:import`는 `storage_removed`로 중단해 삭제한 음악을 자동 재업로드하지 않는다.

사용 완료 후 결과 조회·재생·추가 다운로드는 HTTP 410과 `consumed` 상태를 반환한다. 페이지는 플레이어·다운로드 버튼을 없애고 메모리의 재생 음원을 해제한다. 재생 자체는 권한을 소진하지 않는다. 다른 탭에서 이미 전달받은 오디오 바이트를 회수하는 기능은 아니다.

## 서버 오류와 전송 경계

DB 트랜잭션과 브라우저 파일 저장은 하나의 트랜잭션이 아니다. DB에 사용 완료를 기록한 직후 서버가 중단되거나 전송이 끊기면, 사용자가 파일을 받지 못했어도 권한이 사용될 수 있다. 브라우저가 저장 완료했는지를 성공 기준으로 삼지 않는다. 서버가 바이트를 준비하지 못한 오류는 확정 전 점유 해제를 시도한다.

사용 완료 확정 시 삭제 대기를 DB에 함께 기록하므로, 서버가 중단돼도 삭제해야 할 상태가 남는다. 현재는 응답 후 삭제 1회와 운영자의 수동 삭제 재개를 제공한다. 정기 복구 작업·Cron은 배포하지 않았다. 실패 로그는 고정 오류 코드·HTTP 상태만 사용하며 키·토큰·원문·오브젝트 경로를 출력하지 않는다.

[Supabase CDN 문서](https://supabase.com/docs/guides/storage/cdn/smart-cdn)에 따르면 삭제 전파에 지연이 있을 수 있다. 서비스는 Storage URL이나 서명 URL을 사용자에게 주지 않고 매 요청마다 DB의 사용 완료 상태를 검사하므로, 캐시 무효화가 끝나기 전에도 새 재생·다운로드 요청을 차단한다. 별도 검증 시에는 `cacheNonce`를 붙인 조회로 원본 서버의 누락 응답도 확인한다.

```sh
# Secret은 기존 서버 환경변수 사용. 사용 완료된 곡에 대해서만 삭제를 점유한다.
SUPABASE_URL=https://fuvgpqkyhuyanbfavwcg.supabase.co npm run result:cleanup -- --song-id <UUID> --allow-storage-delete
```

사용하지 않은 링크에는 삭제 권한을 얻지 못한다. 이미 삭제 완료이거나 다른 작업이 삭제 중이면 `not_claimed`를 반환한다. 삭제 완료 기록 응답을 잃었더라도 같은 명령은 기존 완료 상태를 유지하며, 파일이 먼저 삭제됐으면 누락된 파일의 삭제를 반복하는 것은 안전하다.

## DB와 테스트

마이그레이션 `20261026200705_single_download_cleanup.sql`을 실제 프로젝트에 한 번 적용했다. 링크 테이블의 RLS와 서버 전용 권한을 유지하고 점유·확정·해제·삭제 함수 6개를 추가했다. 네트워크 요청을 DB 트랜잭션 안에 넣지 않으며, 점유 UUID와 만료 시각으로 오래된 작업이 새 작업의 상태를 변경하는 것을 막는다.

- 로컬 PostgreSQL 엔진에서 익명·로그인 사용자의 함수 접근 차단, 중복 점유, 취소·만료 거부, 점유 교체, 사용 완료 후 해제 불가, 부분 삭제 후 재개를 검증한다.
- HTTP 테스트에서 중복 요청 중 한 건만 성공, 준비 실패 후 수동 재시도, 확정 응답 유실 후 재다운로드 차단, 요청 중 연결 끊김, 응답 후 정리 콜백을 확인한다.
- 여러 음원 ZIP은 독립적인 Python `zipfile`로 CRC와 모든 원본 해시를 비교한다.

### 실제 검증 (2026-10-27 KST)

- `npm test`: 64개 통과. 삭제 확인에 CDN 다운로드 응답을 쓰지 않는 회귀 테스트와 정리 점유 요청 실패의 안전한 오류 처리도 포함한다.
- 기존 MP3를 별도 UUID의 검증용 복사본으로 저장해 실제 DB·Storage·브라우저를 연결했다. DB의 동시 점유 요청 2개 중 1개만 성공했다. 원래 음악의 권한은 사용하지 않았다.
- Chromium에서 저장한 MP3는 3,021,074바이트이며 SHA-256 `bd4905f2f0b26e675b154e11e1a59851c6f13c987dbf0880487f54d442fda102`로 원본과 일치했다. 재다운로드는 HTTP 410, 플레이어·버튼은 숨김 상태였다.
- 별도의 모의 API 브라우저 검증에서 음원 로딩·다운로드 경합, 준비 오류 후 직접 재시도 가능 상태, 확정 응답 유실 후 사용 완료 화면을 확인했다. 자동 다운로드 POST 재시도는 없었다.
- 수정 전 검증에서 삭제 후 GET 응답을 기준으로 한 확인이 실패 상태로 남았으며, 삭제만 수동 재개해 완료했다. 삭제 완료 확인을 POST 목록 조회로 바꾼 뒤에는 첫 자동 삭제가 `deleted`로 완료됐다. 메타데이터의 부재와 `cacheNonce`를 사용한 재조회 누락 응답도 확인했다.
- 검증용 Interaction 표시는 `verification:download:`로 분리했다. 검증 후 파일 삭제가 끝난 해당 테스트 레코드만 정리했다. 최종 DB는 원래 음악 1개·파일 메타데이터 1개·저장 이벤트 3개·결과 링크 1개로 돌아왔고, 원래 음악은 `stored`, 원래 링크는 미사용 상태다.
- 보고서·다운로드 파일·모바일 캡처는 Git 제외 경로 `artifacts/download-live/`에 보존했다. 키나 원본 토큰은 보고서에 넣지 않았다. 보안 Advisors는 ERROR/WARN 없이 기존 서버 전용 테이블의 INFO만 반환했다.

7일 만료 자체의 접근 차단은 기존 서버에 있다. 만료된 미사용 파일의 자동 삭제·재신청·50일 경계·이메일·외부 배포는 이번 구현에 포함하지 않는다.
