## 흐름

1. ChatGPT 로그인 없이 Site에서 입장 비밀번호를 입력한 뒤 사연·옵션을 입력하고 노래 신청하기를 누른다. 수신 이메일은 빈칸에서 시작하며 사용자가 입력한 주소를 해당 신청의 수신처로 저장한다.
2. Site 서버가 제출 내용을 검증하고, 새 페이지 토큰을 생성해 AES-256-GCM으로 암호화한다. 브라우저에 원본 토큰이나 서버 키를 요구하지 않는다.
3. 서버 전용 접수 키로 Edge API에 접수한다. Edge API는 서버에서 프롬프트를 구성하고 RLS가 적용된 서비스 전용 DB에 접수한다. 새 접수 키는 Google/Gmail 인증값과 별개이고, DB에는 접수 키 해시만 있다.

5. 완료 오디오를 크기·해시·MIME와 함께 등록하고 비공개 Storage에 저장·재검증한다. 새 곡의 고정 결과 페이지를 발급한다.
6. 기존 완료 안내 outbox와 차수별 중복 방지를 사용해 결과 링크를 Gmail로 1회 발송한다. 음악 파일을 첨부하지 않는다. Gmail 접수와 받은편지함 수신을 구분한다.
7. 결과 페이지에서 재생과 1회 다운로드를 제공한다. 재생은 다운로드 횟수를 소진하지 않는다. 다운로드 전송 시작 시 소비 확정 후 음원을 삭제하는 기존 정책을 유지한다.

## 개발용 작업자와 Secret

Gemini/Gmail Secret은 원래 클라우드 환경에만 준비돼 있고 Supabase 함수에는 없다. 기존 인증값을 다른 서비스로 복사하거나 출력하지 않고, 현재 클라우드 작업자가 정상 SDK/프록시 경로로 처리하게 했다. Supabase가 제공하는 서비스 역할 키는 Edge Function 내부에서만 사용한다.

Site의 `REQUEST_INGRESS_KEY`, `REQUEST_ENCRYPTION_KEY`는 새로 만든 앱 전용 Secret이다. Sites 네이티브 Secret 저장소에만 설정했다. 클라우드 작업자가 사용할 동일 앱 설정은 Git 제외 `artifacts/request-service/runtime.json`에 0600으로 보관한다. 키·토큰·사연·원문 응답은 로그에 출력하지 않는다. 이 파일이 없는 새 환경에서 키를 임의로 다시 만들면 기존 접수 토큰을 복호화할 수 없으므로, 기존 보관 자료를 먼저 연결한다.

```sh
npm run requests:worker
```

작업자는 시작할 때 Gmail 토큰 갱신·발신 계정 일치를 확인하고 10초마다 heartbeat를 기록한다. heartbeat가 60초 넘게 끊기면 신규 신청 버튼이 비활성화된다. 최근 24시간 최대 50건, 동시 활성 신청 1건이다. 이는 공용 입장 비밀번호를 아는 테스트 이용자 전체에 적용되는 제한이다.

**상시 운영 서버는 아직 아니다.** 현재 클라우드 환경과 작업자 프로세스가 살아 있을 때 처리한다. 환경 중지·프로세스 종료 뒤에도 DB 접수·상태는 보존하지만 자동 재기동/24시간 가용성을 보장하지 않는다. 장기 운영에는 Google/Gmail 인증이 준비된 상시 작업자 호스팅을 마련해야 한다.

Site 접근 모드는 사용자의 명시적 요청에 따라 `public`이다. 플랫폼 로그인 대신 서버에서 입장 비밀번호를 검증한다. Site의 `SITE_PASSWORD`, `SITE_SESSION_KEY`는 Secret이다. 원문 비밀번호를 소스·Git·문서에 기록하지 않는다. 로그인 성공 시 8시간짜리 Secure/HttpOnly/SameSite=Lax HMAC 쿠키를 발급한다. 비밀번호나 서명 키를 바꾸면 기존 세션은 무효다. 잘못된 시도 5회/10분은 5분 차단하며, DB에는 IP 원문 대신 HMAC 식별자만 저장한다.

HTML과 모든 고객 API에 같은 입장 권한을 적용한다. 결과 페이지는 같은 원점의 Site 서버를 통해 Edge에 접속하며, 플랫폼 사용자 헤더로 입장 권한을 대체하지 않는다. Edge의 `/api/*` 직접 호출도 앱 전용 접수 키 없이는 차단한다. 고객의 결과 토큰은 이와 별도로 계속 필요하다. 로그인은 결과 페이지의 원래 URL에서 처리해 `#token`을 유지한다. 비밀번호 변경 전부터 열어 둔 탭이나 세션 만료 시 페이지를 새로고침하고 입장한다.

## 상태와 재처리

`accepted` → `generating` → `saving` → `notifying` → `completed`.

`unknown`은 생성 POST 응답 손실 등 결과 불명이다. `failed`는 저장·확인 실패 등이며 이미 생성됐을 수 있다. `mail_failed`·`mail_unknown`은 음악은 준비됐지만 메일 처리가 실패/불명인 상태다. 자동으로 다시 생성하거나 다시 발송하지 않는다. claim은 `accepted`만 처리하며 이미 점유된 생성 작업은 재점유하지 않는다. 무작정 상태를 accepted로 바꾸지 않는다.

## 신청 버튼 재발 수정 — 2026-10-27 23:47 UTC

구버전 탭의 `/api/request/health`가 반복 401을 받는데도 재입장 안내를 하지 않았고, 대화 실행에 붙어 있던 작업자가 종료돼 heartbeat도 stale이었다. 비밀번호 이전 탭과 세션 만료는 작성한 사연을 유지하는 인라인 비밀번호 창으로 복구한다. 인증 복구 후 읽기 전용 상태 확인만 재개하며 신청 POST를 자동 반복하지 않는다. 상태 요청에 20초 제한을 추가했다.

음악 처리 작업자는 `nosayeon-request-worker`라는 detached Docker 컨테이너로 전환했다. `unless-stopped` 재시작 정책, non-root/read-only/cap-drop, 프로세스·메모리·로그 제한을 적용했다. 앱 설정은 기존 private runtime.json을 읽기 전용 마운트하고, 환경 인증은 기존 프록시와 CA를 사용한다. 이미지/소스에 키를 넣지 않는다. 작업자의 Google 생성/복구/메일 중복 방지 정책은 그대로다. **재시작은 프로세스 재시작이며 이미 점유된 작업의 재생성·재발송은 아니다.**

```sh
BUILDX_CONFIG=/tmp/nosayeon-buildx docker build -f Dockerfile.request-worker -t nosayeon-request-worker:current .
node scripts/start-request-worker-container.mjs
docker inspect --format '{{.State.Status}} restart={{.HostConfig.RestartPolicy.Name}}' nosayeon-request-worker
```

기존 컨테이너/작업자가 있으면 런처는 새 작업자를 만들지 않는다. 코드 업데이트 시 활성 작업·큐를 확인하고 안전하게 기존 컨테이너를 중지·교체한다. 환경 자체가 중지되거나 프록시/Secret 세션이 바뀌면 가용성을 보장하지 않는다. 독립적인 상시 호스팅은 아직 후속 과제다.
