# 고정 결과 페이지와 동일 음악 재신청

## 구현

[확정 정책](PRODUCT_POLICY.md)에 따라 `POST /api/restore?id=<UUID>&version=<현재 차수>`를 추가했다. 결과 페이지의 기존 Bearer 토큰을 사용하고 DB가 최초 생성 후 50일 자격을 다시 검사한다. 유효한 다운로드가 있는 경우와 사용 완료·만료된 경우 모두 신청할 수 있으며 횟수 제한은 없다.

1. 곡·페이지 행을 잠가 재신청을 한 작업만 점유한다. 현재 차수와 다른 요청은 HTTP 409로 거부한다.
2. 기존 다운로드 점유를 무효화하고 페이지를 준비 중 상태로 바꾼다. 기존 파일 경로와 새 파일 경로를 각각 기록한다.
3. 이전 음원을 Storage API로 삭제하고 목록에서 사라졌음을 확인한다. 이후에만 기존 Google Interaction을 GET으로 조회한다.
4. ID·모델·생성 시각·파일 수·MIME·크기·최초 해시를 검증한 오디오만 새 차수에 저장하고, 실제 저장 바이트를 다시 읽어 검증한다.
5. 저장 완료 시각부터 7일의 새 다운로드 기간을 열고, 페이지의 원래 토큰과 최초 생성 시각은 유지한다. 메일·카톡 완료 안내용 이벤트를 기록한다.

파일 경로는 최초 `song_id/original/...`, 재신청 후 `song_id/revisions/<차수>/original/...`이다. 삭제 작업도 점유 시점의 파일 목록 스냅샷만 사용한다. 오래된 작업의 삭제 요청·완료 응답이 새 음원을 삭제하거나 새 권한을 소진하지 못하도록 분리했다. 실제 삭제된 파일의 최초 메타데이터는 유지한다.

실패하거나 서버가 중단되면 원래 페이지에서 실패·진행 상태를 확인할 수 있다. 사용자는 직접 재신청한다. 재시도 전에 남은 이전·부분 저장 파일을 정리하고, 새 차수 경로를 사용한다. 10분 점유가 끝난 중단 작업은 정리 워커가 실패 상태로 전환해 부분 파일도 삭제한다. 복구를 위해 생성 POST를 호출하지 않는다.

페이지를 아직 발급하지 않은 저장 파일도 저장 후 7일이 지나면 자동 정리한다. 이후 페이지를 발급해도 저장 보관기간을 연장하지 않으며, 50일 자격이 남았다면 같은 페이지에서 재신청할 수 있다.

## 고정 주소와 새로고침

페이지 주소의 곡 ID와 `#token=...` fragment를 유지한다. fragment는 HTTP 요청 URL이나 Referer로 전송되지 않고 API에는 Authorization 헤더로만 토큰을 보낸다. Referrer-Policy는 `no-referrer`이고 외부 리소스를 추가하지 않았다. 토큰을 콘솔·서버 로그·브라우저 저장소에 넣지 않는다. 주소 자체는 음악에 접근할 수 있는 비공개 주소로 취급한다.

이는 이전 검증 화면의 주소창 토큰 제거 방식에서 변경한 부분이다. 새로고침과 다시 방문을 위해 주소를 유지하며, 결과를 서버에서 다시 조회한다. 처리 중 새로고침해도 서버 작업은 이어지고 페이지는 상태 조회만 반복한다. 자동 재신청 POST나 자동 음악 생성은 없다.

사용자 결과 API는 기존 `npm run result:serve` 로컬 서버에 연결했다. 서버의 `GEMINI_API_KEY`가 없으면 기존 권한·파일을 바꾸기 전에 재신청을 거부한다. 공개 결과 서비스 호스팅과 실제 알림 전송은 아직 배포하지 않았다. 자동 정리 Edge Function은 새 경로·스냅샷을 처리하도록 버전 2로 갱신했다.

## 알림 상태

`song_notification_outbox`에 곡 ID·차수·`reissue_ready` 이벤트를 한 번 기록한다. 상태는 `pending_setup`이다. 수신 이메일·전화번호·발신 자격 증명·카톡 제공사를 정하지 않은 상태에서 보내거나 전송됐다고 표시하지 않는다. 전송 연동 시 같은 결과 페이지를 재안내해야 하며, 비공개 페이지 주소를 안전하게 구성·전달하는 처리도 함께 연결해야 한다.

실제 전송 작업에서는 `verification:`으로 표시한 검증 데이터를 제외해야 한다. 현재 검증용 이벤트도 외부로 발송하지 않았다. 단순 새 링크 발급이나 원래 페이지 토큰 교체로 이 정책을 대체하지 않는다.

## 적용·검증

- 실제 마이그레이션: `20261026220530_stable_page_reissue`, `20261026222405_index_restore_request_reference`.
- 새 재신청·스냅샷 함수와 두 테이블은 RLS·서버 전용 권한을 사용한다. 익명·로그인 역할은 접근·실행할 수 없다.
- `npm test`: 93개 통과. 로컬 SQL·메모리 Storage를 함께 사용해 재신청 4회, 50일 경계, 이전 삭제 작업과의 경합, 조회 실패 후 재개, 중단된 작업의 부분 파일 정리, 페이지 미발급 파일의 만료를 검증했다.
- 실제 복사본에서 Google GET 복구 3회와 실제 DB·Storage·Chromium을 연결했다. 유효한 다운로드 교체, 다운로드 후 재신청, 처리 중 새로고침, 동일 주소 유지, 이전 차수/동시 요청의 HTTP 409를 확인했다.
- 복사본은 별도 `verification:reissue:` ID로 분리했고 테스트 주입 계층에서만 실제 원본 Interaction을 조회했다. 운영 코드는 해당 곡의 DB Interaction ID를 그대로 사용한다. 새 음악 생성 요청은 0회다.
- 다운로드한 실제 MP3는 3,021,074바이트, SHA-256 `bd4905f2f0b26e675b154e11e1a59851c6f13c987dbf0880487f54d442fda102`로 최초 원본과 일치했다. 원본 음악과 원본 페이지 권한은 사용하지 않았다.
- 검증용 음원 파일은 최종 다운로드 후 삭제했다. 검증 처리·알림 대기 기록도 해당 테스트 ID만 조건으로 정리했고 원래 음악 1개·파일 1개·결과 페이지 1개를 유지했다. 메시지는 발송하지 않았다. 보고서·화면 캡처는 Git 제외 경로 `artifacts/reissue-live/`에 보존한다. 원본 페이지 토큰과 API 키는 보고서에 넣지 않았다.

메일·카톡 채널과 수신처를 연결하기 전에는 재알림 발송이 완료됐다고 판단하지 않는다.
